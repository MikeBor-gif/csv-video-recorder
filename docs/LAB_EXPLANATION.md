# Объяснение лабораторной работы: теория, код и запуск

Подробное учебное пособие по проекту Browser Video Recorder. Основной акцент — Internship Task 3: загрузка компаний из CSV в PostgreSQL и извлечение реквизитов из Impressum через DeepSeek. Предыдущие задания разобраны как основа этой системы: рекордер, веб-сервис в Docker и обработка зума.

Документ объясняет реализованный код, а не историю отдельных коммитов. Команды и ограничения сверены с файлами проекта. Описанные ожидаемые результаты нужны для самостоятельной проверки; они не означают, что при подготовке этого текста повторно запускались контейнеры, запись видео или платный API.

## 1. Что требовалось по методичке

### 1.1. Как связаны задания

Проект состоит из нескольких последовательных расширений. Их нельзя считать разными названиями одного задания: у каждого свои требования.

| Источник | Задача | Основные файлы |
|---|---|---|
| `TEST_TASK_v2 (1).pdf` | Читать CSV, выполнять браузерный сценарий и записывать видео с визуальными эффектами | `capture_video.py`, `qscript.py` |
| `TEST_TASK_v3.pdf` | Загружать видео на сервер, хранить метаданные и получать URL для просмотра | `web_service.py`, `video_client.py` |
| `INTERNSHIP_TASK_1.pdf` | Запускать Apache + mod_wsgi + Flask и PostgreSQL в двух контейнерах | `Dockerfile`, `docker-compose.yml`, WSGI и Apache-конфигурация |
| `INTERNSHIP_TASK_2.pdf` | Собирать события приближения, применять плавный зум через ffmpeg внутри Docker | `zoom_events.py`, `apply_zoom.py`, расширения рекордера и сервиса |
| `INTERNSHIP_TASK_3.pdf` | Импортировать компании, находить Impressum, извлекать реквизиты через DeepSeek и экономить токены | `company_data.py`, `impressum.py`, `enrich_companies.py` |

Internship Task 1 заменяет прежнее хранилище SQLite на PostgreSQL. Internship Task 2 разрешает необходимые изменения рекордера для сбора зума. Task 3 добавляет новую предметную область — компании, сохраняя существующие API видео и обработки.

### 1.2. Цель Task 3 простыми словами

На входе есть таблица компаний с названием и сайтом. Нужно загрузить её через браузер, сохранить в БД, затем отдельной программой посетить сайт каждой компании, найти страницу Impressum/Imprint и превратить текст реквизитов в структурированные поля.

Ключевая учебная задача — подготовка текста для языковой модели. В HTML много меню, скриптов, повторяющихся ссылок и служебных элементов. Отправлять всё дорого и менее удобно для извлечения. Поэтому программа сначала получает полезный текст и сокращает длинные страницы по юридическим признакам.

Результат должен храниться в PostgreSQL и читаться через HTTP API. Ошибка одной компании не должна останавливать весь список. Повторная загрузка CSV не должна стирать уже найденные реквизиты.

### 1.3. Что считается результатом работы

Результат — работающий путь данных: CSV → PostgreSQL → сайт → Impressum → подготовленный текст → DeepSeek → проверенный JSON → PostgreSQL → HTTP API.

Полный адрес означает наличие четырёх компонентов: `street`, `house_no`, `postcode`, `city`. По методичке страна, VAT, телефон и ответственное лицо не обязательны для статуса `OK`. Это критерий лабораторной, а не проверка юридической достаточности Impressum.

## 2. Общая архитектура

### 2.1. Два независимых потока данных

```text
Поток компаний:
браузер / CSV
    → Apache :80 в web
    → mod_wsgi → Flask → company_data.py → PostgreSQL в db

отдельный запуск enrich_companies.py
    → чтение companies
    → impressum.py → сайт → текст → DeepSeek
    → запись результата в companies

Поток видео:
input.csv → capture_video.py → qscript.py → Chromium → WebM + sidecar
    → video_client.py → HTTP upload → Flask → uploads + videos/jobs
    → apply_zoom.py → ffmpeg → обработанный WebM → URL просмотра
```

CLI обогащения и веб-приложение используют общую БД, но запускаются как отдельные процессы. Импорт CSV не вызывает DeepSeek автоматически. Это позволяет проверить форму и API без ключа и без расходов.

### 2.2. Назначение файлов

| Файл | Что делает | Зачем выделен |
|---|---|---|
| `company_data.py` | Конфигурация БД, таблица companies, CSV, SQL, статусы | Одинаковые правила для Flask и CLI |
| `impressum.py` | Загрузка сайтов, поиск ссылки, очистка и сокращение текста, DeepSeek | Можно отдельно проверять обработку HTML и ответов API |
| `enrich_companies.py` | Аргументы командной строки и цикл обработки | Управляет работой без зависимости от Flask |
| `web_service.py` | HTTP-маршруты, видео, jobs, компании | Принимает запросы пользователя и клиента |
| `capture_video.py` | Чтение CSV рекордера и вызов сценария | Отделяет ввод данных от браузерной логики |
| `qscript.py` | Сценарий, курсор, подсветка, callout, zoom capture | Содержит взаимодействие с Chromium |
| `video_client.py` | Загрузка, получение URL и просмотр | Рекордер не должен знать внутреннее устройство сервера |
| `zoom_events.py` | Валидация sidecar и математика переходов | Чистую логику можно тестировать без браузера и ffmpeg |
| `apply_zoom.py` | Формирование фильтра и запуск ffmpeg | Изолирует кодирование видео |
| `web_service.wsgi` | WSGI-точка входа | Соединяет приложение с Apache |
| `apache/video-service.conf` | Настройки Apache и раздачи `/media/` | HTTP-инфраструктура отделена от Python-кода |
| `scripts/verify_companies.py` | Сквозная проверка компаний | Проверяет уже работающий сервис |
| `tests/` | Автоматические проверки | Позволяют обнаруживать нарушения контрактов |

### 2.3. Почему видео и компании в разных таблицах

`videos` хранит сведения об оригинальных роликах, `jobs` — состояние обработки конкретного видео, `companies` — исходные сведения и извлечённые реквизиты. Это разные сущности с разным жизненным циклом.

Изменение адреса сайта компании не должно менять видео, а повторная обработка зума не должна влиять на юридические реквизиты. Совпадение названий не создаёт в коде автоматической связи через внешний ключ между этими таблицами.

## 3. Теория Python и разделения кода

### 3.1. Модуль, функция и точка входа

Модуль Python — файл `.py`, содержащий функции, классы и константы. Импорт позволяет повторно использовать эти определения. Функция получает аргументы, выполняет ограниченную задачу и возвращает результат.

Конструкция `if __name__ == "__main__":` отделяет запуск файла как программы от его импорта. Например, импортировать функции обработки текста для теста можно без автоматического запуска всего CLI.

CLI означает command-line interface — интерфейс командной строки. `argparse` разбирает флаги вроде `--limit 2`, проверяет допустимые значения и формирует справку `--help`.

### 3.2. Зачем нужна декомпозиция

Если HTTP-маршрут одновременно читает CSV, формирует SQL, скачивает сайты и вызывает модель, его трудно проверять и повторно использовать. Здесь обязанности разделены: маршрут принимает запрос, слой данных работает с БД, модуль Impressum обрабатывает внешний текст, CLI управляет последовательностью.

Такое разделение помогает локализовать ошибку. Неверный формат CSV исследуется в `parse_company_csv()`, а неверный статус после ответа модели — в `extraction_result()`.

### 3.3. Исключения и освобождение ресурсов

Исключение — сигнал о том, что обычное выполнение невозможно. В проекте есть предметные типы: `CompanyCSVError`, `FetchError`, `DeepSeekError`, `ZoomError`. По типу вызывающий код определяет, как обработать отказ.

`try/except` перехватывает ожидаемую ошибку. `finally` выполняет завершающие действия независимо от успеха: закрывает сессию, браузер или удаляет временный файл.

Контекстный менеджер `with` организует жизненный цикл ресурса. В `company_data.py` сочетание `closing(connect(config))` и контекста соединения даёт закрытие соединения и управление транзакцией: commit при успехе, rollback при исключении.

### 3.4. Константы и IntEnum

Константы вроде `MAX_TEXT_CHARS` называют ограничения и помогают избежать случайных чисел в алгоритме. `CompanyStatus(IntEnum)` задаёт именованные целочисленные состояния: в Python удобно читать `CompanyStatus.OK`, в PostgreSQL хранится `0`.

Единое определение статусов исключает ситуацию, когда CLI считает ошибкой одно число, а API показывает другое.

## 4. Теория HTTP, Flask, Apache и WSGI

### 4.1. Запрос и ответ

HTTP связывает клиента и сервер. Запрос содержит метод, путь, заголовки и иногда тело. Ответ содержит код состояния, заголовки и тело.

| Элемент | Пример | Смысл |
|---|---|---|
| Метод | `GET` | Получить представление ресурса |
| Метод | `POST` | Передать данные для обработки |
| Путь | `/companies` | Выбрать обработчик |
| Query parameter | `?status=0` | Передать фильтр |
| Content-Type | `application/json` | Описать формат тела |
| Код | `200` | Успешное выполнение |
| Код | `400` | Некорректный запрос |
| Код | `404` | Ресурс не найден |
| Код | `413` | Превышен лимит загрузки |
| Код | `500` | Ошибка на сервере |

JSON — текстовый формат объектов, массивов, строк, чисел, `true`, `false`, `null`. Он удобен для API, потому что его легко читать программно. HTML предназначен для отображения страницы браузером. Поэтому форма возвращается как HTML, а список компаний — как JSON.

### 4.2. Зачем multipart/form-data

При загрузке файла тело запроса должно содержать его байты и имя поля. Для этого HTML-форма использует `enctype="multipart/form-data"`. В Task 3 имя файлового поля — `file`.

Атрибут `accept=".csv"` помогает выбрать файл в браузере, но не является проверкой содержимого. Сервер всё равно проверяет UTF-8, заголовки и строки CSV.

### 4.3. Роль Flask

Flask сопоставляет URL с Python-функцией, предоставляет данные запроса и формирует ответ. `request.files` содержит загруженные файлы, `request.args` — параметры после `?`, `jsonify()` формирует JSON-ответ.

`create_app()` — фабрика приложения. Она создаёт экземпляр Flask, задаёт настройки, инициализирует БД и регистрирует маршруты. В тестах можно передать отдельную конфигурацию и временную папку загрузок.

### 4.4. Зачем Apache и mod_wsgi

По Internship Task 1 HTTP-сервером должен быть Apache. WSGI — интерфейс между Python веб-приложением и сервером. `mod_wsgi` загружает Python-приложение и передаёт ему запросы Apache через этот интерфейс.

Цепочка выглядит так: браузер → Apache → mod_wsgi → Flask → Python-функция. Файл `web_service.wsgi` предоставляет объект `application`, который вызывает сервер.

В конфигурации используется daemon process с потоками. Поэтому нельзя раздавать одно изменяемое соединение psycopg2 всем запросам. Сервис получает соединение через контекст запроса и закрывает его при завершении.

### 4.5. Раздача медиа

В контейнере Apache обслуживает `/media/` непосредственно из `/app/uploads/`. Это позволяет передавать видео и поддерживать Range-запросы без выполнения Python для каждого фрагмента файла. Range-запрос запрашивает часть файла и нужен, например, для перемотки.

Скрытая папка `.jobs` содержит внутренние snapshots и закрыта конфигурацией Apache. В dev-режиме медиа обслуживает маршрут Flask.

## 5. Теория Docker и Docker Compose

### 5.1. Образ и контейнер

Образ Docker — подготовленная файловая система с приложением и зависимостями. Контейнер — запущенный процесс на основе образа. `Dockerfile` описывает сборку образа: базовый Python, системные пакеты, Python-зависимости, копирование кода и команду запуска.

В этом проекте основа `web` — `python:3.12-slim-bookworm`. В образ устанавливаются Apache, mod_wsgi, ffmpeg и Python-библиотеки. Запуск `apache2ctl -D FOREGROUND` оставляет основной процесс в foreground, чтобы Docker отслеживал его состояние.

Наличие Playwright как Python-пакета в образе не означает наличие установленного Chromium. Основной путь записи браузерного видео в инструкции — на компьютере пользователя.

### 5.2. Зачем два сервиса

`web` содержит веб-приложение, `db` — PostgreSQL 16. У них разные роли, процессы, настройки и данные. Compose описывает их совместный запуск, сеть, тома и проверки готовности.

В сети Compose имя `db` разрешается в адрес контейнера PostgreSQL. Поэтому `DB_HOST=db` корректен внутри `web`. `localhost` внутри `web` означает сам `web`, а не соседнюю БД и не Windows-компьютер.

### 5.3. Что означает 8000:80

Запись `8000:80` публикует порт 80 контейнера `web` на порту 8000 компьютера. Из браузера Windows используется `http://localhost:8000`. Из процесса внутри `web` Apache доступен как `http://127.0.0.1` на порту 80.

PostgreSQL работает на 5432 внутри сети Compose. В текущем файле Compose его порт наружу не опубликован. Поэтому локальный CLI не подключится к контейнерной БД только от установки `DB_HOST=localhost`; проще выполнять CLI через `docker compose exec`.

### 5.4. Зачем нужны тома

Файлы в изменяемом слое контейнера могут исчезнуть при его удалении. Named volume — отдельное постоянное хранилище, подключённое к контейнеру.

| Том | Куда подключён | Что хранит |
|---|---|---|
| `db_data` | `/var/lib/postgresql/data` в `db` | Таблицы и служебные данные PostgreSQL |
| `uploads` | `/app/uploads` в `web` | Загруженные и обработанные видео, внутренние файлы jobs |

`docker compose down` останавливает и удаляет контейнеры и сеть, сохраняя named volumes. Добавление `-v` удаляет тома вместе с данными; для обычного завершения лабораторной этот флаг не нужен.

### 5.5. Healthcheck и готовность БД

Запущенный процесс БД ещё не обязательно готов к SQL-запросам. Проверка `pg_isready` определяет готовность PostgreSQL. `depends_on` с `condition: service_healthy` связывает старт `web` с успешной проверкой `db`.

Дополнительно приложение повторяет подключение при старте. Healthcheck `web` вызывает `/health`, который проверяет доступность БД. Это полезнее проверки одного лишь факта существования процесса Apache.

### 5.6. Переменные окружения и .env

Переменные окружения — параметры процесса, доступные через `os.environ`. Они отделяют код от адресов, паролей и ключей.

Compose читает `.env` для подстановки значений в YAML и передаёт указанные переменные в контейнер. Обычный запуск `python enrich_companies.py` автоматически `.env` не читает. Пакета dotenv в этом проекте нет.

Ключ DeepSeek хранится только в локальном окружении или `.env`, исключённом из Git и Docker image. После изменения окружения нужно пересоздать контейнер через `docker compose up -d`; `restart` перезапускает его с прежними переменными.

## 6. Теория PostgreSQL и модели данных

### 6.1. Реляционная таблица

Таблица состоит из строк и колонок. Строка `companies` описывает одну компанию, колонка — одно свойство. SQL используется для создания структуры, чтения и изменения данных.

В проекте применяется драйвер `psycopg2`, а ORM нет. ORM — библиотека, представляющая таблицы как объекты и генерирующая запросы. Здесь SQL записан явно, что делает правила импорта и конкурентного обновления видимыми.

### 6.2. Ключи и ограничения

`id SERIAL PRIMARY KEY` создаёт числовой идентификатор. Первичный ключ однозначно определяет строку. `company_name TEXT NOT NULL UNIQUE` запрещает отсутствие названия и одинаковые названия в нескольких строках.

Уникальность работает по значению, которое передаёт программа: импорт не приводит имена к нижнему регистру и не удаляет все пробелы перед сохранением. `ACME` и `acme` могут быть разными ключами. Проверка `.strip()` нужна для отклонения пустого названия, но сама по себе не переписывает исходную строку.

### 6.3. Группы колонок companies

| Группа | Колонки | Источник |
|---|---|---|
| Идентификация | `id`, `company_name` | БД и CSV |
| Исходные сведения | `language`, `country`, `postcode`, `city`, `street`, `house_no`, `web` | CSV |
| Состояние | `status`, `impressum_url` | Обогащение |
| Извлечённые реквизиты | `legal_name`, `postal_address`, `handelsregister`, `vat_number`, `phone`, `email`, `responsible_person` | Проверенный результат модели |
| Полный структурированный ответ | `raw_json` | Распарсенный JSON из содержимого ответа модели |
| Время | `created_at`, `updated_at` | PostgreSQL |

`raw_json` — результат извлечения, а не весь HTTP-конверт DeepSeek с `choices`, `usage` и заголовками. `usage` используется для журналирования расхода.

Исходные адресные поля CSV и извлечённый адрес различаются. Обогащение сохраняет строку в `postal_address`, а компоненты — в `raw_json.postal_address`; оно не переписывает исходные `city`, `street` и другие CSV-колонки.

### 6.4. Почему TEXT, JSONB и TIMESTAMPTZ

`TEXT` хранит строку без заранее заданной длины. Для индекса и номера дома строковый тип удобен: индекс может начинаться с нуля, а дом может быть `12a`.

`JSONB` хранит JSON в разобранном представлении PostgreSQL. Это позволяет сохранить вложенный адрес и дополнительные поля ответа. JSONB не предназначен для сохранения исходных пробелов и порядка ключей JSON-текста.

`TIMESTAMPTZ` хранит момент времени с учётом часовых поясов. В API timestamps преобразуются в строки ISO-формата через `isoformat()`.

### 6.5. NULL отличается от 0

`NULL` означает отсутствие значения. Для новой компании `status=NULL`: попытки ещё не было. `status=0` означает успешное извлечение с полным адресом.

В SQL `status <> 0` не выбирает NULL-строки: сравнение с NULL не даёт `TRUE`. Поэтому правильный default-фильтр:

```sql
WHERE status IS NULL OR status <> 0
```

### 6.6. Транзакции и атомарность

Транзакция объединяет SQL-операции в логическое целое. `COMMIT` фиксирует изменения, `ROLLBACK` отменяет незавершённые изменения.

CSV сначала полностью валидируется, затем импортируется одной транзакцией. Если последняя строка неверная, не должны сохраниться первые строки. Если ошибка возникает уже при записи в БД, выполняется rollback.

Для обогащения другая граница: результат каждой компании сохраняется отдельной операцией. Поэтому сбой одной строки не отменяет уже сохранённые результаты всего batch.

### 6.7. UPSERT и идемпотентность

UPSERT объединяет вставку и обновление: если уникального ключа нет — вставить, если он уже есть — обновить. PostgreSQL предоставляет `INSERT ... ON CONFLICT ... DO UPDATE`.

Идемпотентность импорта здесь означает отсутствие дубликатов при повторном CSV и сохранение enrichment. `updated_at` при повторе меняется, а счётчик переходит из `imported` в `updated`, поэтому весь HTTP-ответ не обязан быть одинаковым.

### 6.8. Параметризация SQL

Пользовательские значения передаются отдельно от текста SQL:

```python
cursor.execute(
    "SELECT * FROM companies WHERE company_name = %s",
    (company_name,),
)
```

Драйвер трактует значение как данные. Склеивать SQL со значением имени нельзя: это создаёт возможность SQL injection и ломает строки с кавычками. Имена колонок при динамическом построении запроса оформляются через `sql.Identifier`, а значения — через placeholders.

## 7. CSV: формат и безопасный импорт

### 7.1. Почему не split(';')

CSV поддерживает кавычки и разделители внутри значения. Строка с названием `"Example; GmbH"` содержит точку с запятой внутри одного поля. Простой `split(';')` ошибочно разделил бы его на две колонки.

`csv.DictReader` понимает CSV-правила и возвращает словарь по заголовкам. В проекте используются `delimiter=";"`, `quotechar='"'`, UTF-8 с поддержкой BOM через `utf-8-sig`.

BOM — специальная отметка в начале файла, которую некоторые редакторы добавляют к UTF-8. Без её обработки первый заголовок мог бы отличаться от ожидаемого невидимым символом.

### 7.2. Два похожих формата

У рекордера обязательна прежняя шапка из восьми колонок. Task 3 расширяет её колонкой `Web`, но для импорта компаний строго обязательны только `Company Name` и `Web`.

```csv
Company Name;Web
nutrimmun GmbH;nutrimmun.de
Barolo & Champagne GbR;baroloandchampagne.com
```

Полный допустимый заголовок Task 3:

```csv
URL;Company Name;Language;Country;Postcode;City;Street;HouseNo;Web
```

`URL` нужен для совместимости с рекордером и в `companies` не сохраняется. `Web` — собственный сайт компании, с которого начинается поиск Impressum. Путать их нельзя: адрес поисковика из `URL` не является сайтом компании.

### 7.3. Что проверяет импорт

Проверяются кодировка, наличие и уникальность заголовков, отсутствие неподдерживаемых колонок, число значений в каждой строке, непустые обязательные поля и отсутствие NUL-символов.

Проверка завершается до изменения БД. Неверный CSV даёт HTTP 400. Неверный формат не должен превращаться в частично загруженный набор компаний.

### 7.4. Отсутствующая колонка и пустое значение

Если колонка `City` вообще не пришла, импорт не должен менять существующий город. Если колонка пришла и содержит пустую строку, это новое CSV-значение, которое записывается.

`status`, `raw_json` и извлечённые поля не входят в набор обновления CSV. Даже изменение `Web` не сбрасывает успешный статус. Для повторного извлечения ранее успешной компании требуется явный `--status 0`.

## 8. Код company_data.py

### 8.1. Конфигурация и схема

`db_config_from_env()` читает `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` и optional `DB_PORT`, проверяет обязательные значения и числовой порт. `connect()` создаёт соединение с ограничением времени подключения и `RealDictCursor` для строк в виде словарей.

`COMPANIES_SCHEMA_SQL` содержит `CREATE TABLE IF NOT EXISTS companies`. `init_companies()` выполняет SQL в транзакции вызывающего кода, `initialize()` организует отдельное подключение. Один и тот же код используется при старте веб-сервиса и CLI.

Идемпотентное создание таблицы позволяет запускать приложение повторно. Оно не является полноценным механизмом изменения любой старой схемы: `CREATE TABLE IF NOT EXISTS` само не добавляет отсутствующие колонки к уже существующей таблице другой структуры.

### 8.2. parse_company_csv()

Функция принимает байты, декодирует их, создаёт `DictReader`, проверяет шапку и строки, затем возвращает список словарей с именами колонок БД.

Словарь `CSV_FIELDS` задаёт соответствия: `Company Name → company_name`, `HouseNo → house_no`, `Web → web`. Только реально присутствующие заголовки попадают в результат, благодаря чему отсутствующие optional-поля не обнуляются.

### 8.3. import_companies()

Функция получает открытое соединение и уже проверенные строки. Перед импортом берётся advisory lock уровня транзакции. Это согласует параллельные импорты и их счётчики; уникальное ограничение остаётся основой защиты от дубликатов.

Для каждой строки выполняются проверка существования и UPSERT. Список обновлений формируется только из CSV-полей, кроме ключа `company_name`; дополнительно меняется `updated_at`.

Возвращается объект `imported`, `updated`, `total_rows`. Счётчики относятся к строкам: если новая компания дважды встречается в одном CSV, первое вхождение считается вставкой, второе — обновлением.

### 8.4. list_companies() и serialize_company()

`list_companies()` читает строки в порядке `id` и при необходимости добавляет фильтр статуса или точного имени. Значения фильтров параметризованы.

`serialize_company()` преобразует временные значения в строки, пригодные для JSON. Вложенный `raw_json` остаётся объектом.

### 8.5. select_for_enrichment()

Функция строит выборку по `--company`, `--status`, `--limit`. Без явного статуса выбираются NULL и все не-OK записи, в порядке `id`. Фильтры объединяются: `--company` сам по себе не заставляет повторять успешную компанию.

### 8.6. save_enrichment() и optimistic update

Между чтением строки и ответом сайта могут пройти десятки секунд. За это время пользователь может повторно импортировать CSV. Сохранять результат по устаревшему сайту поверх новой строки нельзя.

Вместо долгой блокировки используется optimistic concurrency control — проверка, что версия данных не изменилась:

```sql
UPDATE companies
SET ... , updated_at = clock_timestamp()
WHERE id = %s AND updated_at = %s
```

В условии используется timestamp исходного snapshot. Если обновлена одна строка, сохранение успешно. Если ноль — запись изменилась, результат пропускается с предупреждением.

Во время сетевых запросов соединение БД не удерживается. Это снижает время занятости ресурсов, но не предотвращает два одновременных платных запроса для одной компании: конфликт выявляется только при сохранении.

## 9. Новые маршруты web_service.py

### 9.1. GET /upload_companies

Возвращает минимальную HTML-форму: выбор CSV, кнопку Import и ссылку на JSON-список. JavaScript для импорта не требуется: браузер отправляет обычную multipart-форму.

### 9.2. POST /upload_companies

Маршрут проверяет единственный файл в поле `file`, читает его и вызывает `parse_company_csv()`. Только после успешной валидации получает соединение и вызывает `import_companies()`.

При успехе выполняется commit и возвращаются счётчики. При ошибке psycopg2 выполняется rollback и HTTP 500. Ошибка содержимого CSV возвращается как HTTP 400.

Пример для двух новых строк:

```json
{"imported": 2, "updated": 0, "total_rows": 2}
```

Повтор в той же БД:

```json
{"imported": 0, "updated": 2, "total_rows": 2}
```

### 9.3. GET /companies

Возвращает массив строк, включая исходные данные, статус, извлечённые поля и timestamps. `?status=0` ограничивает выдачу успешными строками. Разрешённые значения фильтра — целые числа 0–5; неверное значение возвращает 400.

Пустая выборка возвращает `[]`. Новая компания имеет `status: null`, а не `0`.

### 9.4. GET /companies/<company_name>

Возвращает одну запись по точному имени либо 404. В URL пробел и `&` кодируются, например `Barolo%20%26%20Champagne%20GbR`. В коде применяется path-конвертер Flask; Apache настроен на передачу имён с закодированным слешем.

### 9.5. Почему отдельный endpoint не запускает модель

Запрос пользователя к списку компаний должен читать сохранённое состояние. Если бы каждый GET вызывал DeepSeek, просмотр страницы зависел бы от внешнего сайта, расходовал деньги и мог менять данные. Обогащение поэтому запускается явно отдельным CLI.

## 10. Impressum и получение HTML

### 10.1. Что означает Impressum

В контексте задания Impressum/Imprint — страница сайта, содержащая сведения об операторе: название, адрес, регистрационные и контактные данные, ответственное лицо. Для лабораторной это источник текста для извлечения.

`Handelsregister` обозначает торговый реестр; в тексте встречаются обозначения `HRB` и `HRA`. `VAT number` — идентификатор, связанный с НДС; немецкий формат в методичке обозначен как `DE` и девять цифр. Эти признаки используются как текстовые ориентиры. Программа не проверяет достоверность номера по государственному реестру.

### 10.2. Нормализация Web

`normalize_website_url()` проверяет значение сайта. Для адреса без схемы добавляется `https://`. Пустой сайт обрабатывается как `NO_WEBSITE`.

Исходное значение в БД сохраняется как пришло из CSV. Нормализация относится к сетевому запросу и не должна незаметно переписывать импортированные сведения.

### 10.3. Поиск ссылки

`find_impressum_url()` разбирает HTML через BeautifulSoup и получает ссылки `<a href="...">`. Сначала проверяет видимый текст после удаления внешних пробелов и приведения к lowercase: точное `impressum` или `imprint`.

Если такой ссылки нет, ищет эти слова в `href`. Это помогает, когда видимое название отличается, а путь имеет вид `/impressum.html`.

Относительный адрес разрешается `urllib.parse.urljoin()` относительно конечного адреса главной страницы после redirect. Например, `/impressum` на `https://example.org/start` превращается в `https://example.org/impressum`.

Отсутствие ссылки даёт статус 1 и не требует вызова DeepSeek.

### 10.4. Requests и ограничения ожидания

Requests выполняет HTTP-запрос и получает HTML. `User-Agent` описывает клиента. Timeout ограничивает ожидание сетевых операций.

Одних connect/read timeout недостаточно для ограничения всей загрузки: сервер может очень медленно присылать небольшие части данных, а redirect добавляет новые запросы. Поэтому реализованы общий deadline 60 секунд и предел страницы 2 MiB распакованных данных.

Реальный fetch выполняется в отдельном процессе, который можно завершить при превышении общего времени. На каждой странице допускается до пяти redirect. Эти ограничения защищают длительность batch и память программы.

### 10.5. Защита от SSRF

SSRF — ситуация, когда сервер по пользовательскому URL обращается к своим внутренним ресурсам. Адрес из CSV нельзя считать доверенным.

Код разрешает публичные IP и блокирует localhost, private, link-local, reserved адреса и смешанные DNS-ответы. Проверка повторяется при redirect. Соединение привязывается к проверенному IP, при этом имя сайта сохраняется в Host и TLS/SNI.

Это уменьшает риск подмены DNS между проверкой и соединением. Для загрузки сайтов отключено использование системного прокси и `.netrc`. Не следует обходить эту защиту, подменяя `Web` на адрес внутреннего сервиса ради демонстрации.

### 10.6. Извлечение текста

`extract_visible_text()` удаляет `script`, `style`, `noscript`, `svg`, `nav`, `header`, `footer`, `form`, затем получает текст и нормализует пробелы, сохраняя строки.

Скрипты содержат программный код, CSS — оформление, навигация — повторяющиеся ссылки. Они редко помогают извлечению реквизитов и увеличивают объём входа модели.

Название функции условно: это текст после удаления заданных тегов, а не точная реконструкция видимости браузера с CSS и JavaScript. Полезные реквизиты внутри удалённого footer тоже могут потеряться. JS fallback в текущем коде не реализован, хотя методичка допускает его как необязательный вариант.

## 11. Оптимизация текста и теория токенов

### 11.1. Что такое токен

Языковая модель обрабатывает текст частями — токенами. Токен может соответствовать слову, части слова, знаку или последовательности символов. Поэтому количество символов и токенов не совпадает.

В лабораторной используется грубая оценка `len(text) // 4`. Она удобна для сравнения до и после, но не заменяет токенизатор. Немецкие слова, Unicode и номера могут менять соотношение.

### 11.2. Почему сокращение полезно

Более короткий вход уменьшает передаваемый объём и потенциальный расход входных токенов. Модель видит меньше повторений и посторонних инструкций страницы. Но слишком сильное сокращение способно удалить адрес или ответственное лицо.

Задача алгоритма — сохранить признаки реквизитов в пределах бюджета. Это компромисс между полнотой и объёмом, а не гарантия идеального выделения на любом сайте.

### 11.3. Порог 8000 символов

`MAX_TEXT_CHARS = 8000`. Если длина текста не превышает порог, `optimize_text()` возвращает его без дальнейшего сокращения. Это уже текст после HTML-очистки.

При превышении порога включается эвристика. Метрики сохраняют исходную и конечную длину, оценку токенов и название стратегии.

### 11.4. Этап 1: удаление boilerplate

Boilerplate — повторяющиеся служебные элементы: меню, языки, cookie-строки, ссылки Datenschutz/AGB, copyright. Их удаление уменьшает шум до поиска юридического блока.

Повторные строки `Impressum`/`Imprint` убираются, но первое вхождение сохраняется как возможный заголовок. Правила не являются универсальным пониманием смысла: они сопоставляют заданные текстовые шаблоны.

### 11.5. Этап 2: начало юридического блока

Регулярное выражение `HEAD` ищет начало: `Impressum`, `Imprint`, `Angaben gemäß § 5 TMG`, `DDG`, `Anbieter`, `Diensteanbieter`.

Код оставляет запас 100 символов перед первым найденным заголовком. Запас сохраняет ближайший контекст, например название компании, стоящее непосредственно перед заголовком.

### 11.6. Этап 3: конец по последнему маркеру

Для хвоста используются телефон `+49`/`0049`, VAT вида `DE` + 9 цифр, email, `HRB`/`HRA`, `Registergericht`, `Amtsgericht`, слова ответственности и управления.

Берётся последнее совпадение из `TAIL` и ещё 400 символов после него. Идея: реквизиты могут продолжаться ниже адреса, поэтому нельзя резать сразу после первого найденного поля.

Упрощённая формула границ:

```text
start = max(0, начало_первого_заголовка - 100)
end = конец_последнего_юридического_маркера + 400
candidate = cleaned[start:end]
```

### 11.7. Этап 4: проверка и fallback

В кандидате проверяются заголовок и хотя бы один сильный сигнал `STRONG`: телефон, VAT, email или реестр. Слова ответственности участвуют в выборе хвоста, но сами по себе не заменяют эту проверку сильного сигнала.

При недостаточных anchors код возвращается к исходному тексту. Это fallback — ослабление оптимизации ради сохранения данных.

Если результат всё ещё длиннее 8000, остаются начальное и конечное окна с разделителем `\n[...]\n`; суммарная длина, включая разделитель, укладывается в бюджет. Информация в середине при этом может потеряться.

### 11.8. Пример расчёта

Допустим, после HTML-очистки получилось 12000 символов. Оценка: 3000 токенов. После выделения блока осталось 4800 символов, то есть примерно 1200 токенов.

```text
сокращение текста = (12000 - 4800) / 12000 × 100% = 60%
```

Это учебный пример, а не измерение данного запуска. Точный расход API включает system prompt, пользовательскую инструкцию, текст и выход модели. В логах `usage` отражает счётчики API, а `before_chars`/`after_chars` показывают эффект локального алгоритма.

### 11.9. Почему не regex для всего извлечения

Regex хорошо находит строгий шаблон вроде VAT или email. Для имени компании, границ адреса, номера дома и ответственного лица формулировки разнообразны. Поэтому регулярные выражения используются для выбора блока, а модель — для структурирования смысла.

При этом модель тоже может ошибаться. Её ответ рассматривается как недоверенный ввод и проверяется локально.

## 12. DeepSeek: запрос, JSON и проверка результата

### 12.1. Устройство запроса

Код обращается к `https://api.deepseek.com/chat/completions` через Requests. Авторизация передаётся заголовком Bearer с ключом из `DEEPSEEK_API_KEY`.

| Параметр | Значение в коде | Назначение |
|---|---|---|
| `model` | Из `DEEPSEEK_MODEL`, fallback `deepseek-chat` | Выбор модели |
| `messages` | System prompt и текст страницы | Инструкция и источник данных |
| `response_format` | `{"type":"json_object"}` | Режим JSON |
| `temperature` | `0` | Снижение вариативности |
| `max_tokens` | `1024` | Максимум выходных токенов |
| `timeout` | `60` секунд | Ограничение ожидания HTTP-запроса |

В `.env.example` явно задан `deepseek-flash`. Это настройка репозитория, а не обещание доступности конкретной модели в будущем. Для `deepseek-flash` и `deepseek-v4-pro` код дополнительно передаёт `thinking: {"type":"disabled"}`. Автоматической смены модели после ошибки нет.

`temperature=0` не доказывает абсолютную воспроизводимость и достоверность. `max_tokens` ограничивает ответ, но не задаёт бюджет входного текста. Для входа используется собственный предел 8000 символов.

### 12.2. Системная инструкция

Prompt требует только JSON, перечисляет ожидаемые ключи, запрещает догадки и требует `null` для отсутствующих данных. В тексте присутствует слово JSON и пример структуры, как требует методичка.

Ожидаемая форма результата:

```json
{
  "company_name": "Example GmbH",
  "postal_address": {
    "street": "Musterstraße",
    "house_no": "12a",
    "postcode": "10115",
    "city": "Berlin",
    "country": "Germany"
  },
  "handelsregister": null,
  "vat_number": null,
  "phone": null,
  "email": null,
  "responsible_person": null
}
```

Это искусственный пример схемы. Значения в реальной БД должны происходить из страницы, а не из этого примера.

### 12.3. JSON mode не заменяет валидацию

Даже корректный JSON может содержать неверный тип: массив вместо адреса, число вместо email или пустой объект. Сначала `_decode_completion()` извлекает `choices[0].message.content`, затем `json.loads()` разбирает текст, затем `normalize_extraction()` проверяет структуру.

Отсутствующие известные ключи допускаются как пустые значения. Дополнительные поля могут сохраниться в `raw_json`, но не участвуют в определении обнаруженных реквизитов.

Во всём объекте проверяются NUL, некорректный Unicode, нечисловые бесконечности/NaN и чрезмерная вложенность. Это предотвращает ошибки сохранения в PostgreSQL и неконтролируемую обработку вложенных структур.

### 12.4. Нормализация и отображение в БД

Строки очищаются от лишних пробелов. Email приводится к lowercase; невалидный или замаскированный адрес превращается в `null` в нормализованной колонке. Исходный распарсенный ответ остаётся в `raw_json`.

`legal_name` берётся из JSON-поля `company_name`, а при его отсутствии — из имени CSV. Fallback помогает отображению, но не считается полем, найденным моделью.

`postal_address` в таблице — соединение непустых компонентов адреса в строку. Вложенный объект сохраняется в `raw_json.postal_address`. Программа не дописывает недостающий индекс или дом по догадке.

### 12.5. Ограниченные повторы

На одну компанию допускается максимум две API-попытки в одном вызове извлечения. Между попытками — задержка одна секунда.

Повтор предусмотрен для транспортной ошибки, HTTP 429, HTTP 5xx и blank/невалидного содержимого JSON. Коды 400/401/402/403 автоматически не повторяются. Невалидный внешний конверт ответа трактуется как ошибка API.

Если после повторов структурированный текст пуст или невалиден, формируется безопасный пустой результат со статусом 2. Если исчерпаны повторы сетевой/API-ошибки, статус 4. Частичный, но валидный результат не отправляется повторно ради заполнения всех полей.

Предел действует на текущий запуск, а не на всю жизнь записи. Default повторно выбирает не-OK компании, поэтому следующий запуск может снова расходовать API.

## 13. Статусы компаний

| Значение | Имя | Что произошло | Что смотреть |
|---|---|---|---|
| `NULL` | pending | Компания импортирована, обработки ещё не было | Запустить CLI |
| `0` | `OK` | Есть обнаруженные поля и все четыре компонента адреса | Проверить содержимое и источник |
| `1` | `NO_IMPRESSUM_LINK_FOUND` | На главной не найдена нужная ссылка | HTML главной и способ рендеринга |
| `2` | `PARSING_FAILED` | Не обнаружены поля либо не получен пригодный JSON после повторов | Структуру ответа, attempts |
| `3` | `ADDRESS_INCOMPLETE` | Поля есть, но адрес неполон | `raw_json.postal_address` |
| `4` | `ERROR` | Ошибка загрузки сайта или API | Тип отказа и HTTP-код в логах |
| `5` | `NO_WEBSITE` | У существующей строки нет сайта | `web` в БД |

### 13.1. Порядок определения после ответа модели

```text
Нет ни одного обнаруженного известного поля?
    да → 2
    нет → street, house_no, postcode, city заполнены?
              да → 0
              нет → 3
```

Порядок существенен: пустой объект должен получить 2, хотя у него также неполный адрес. Статусы 1, 4, 5 относятся к более ранним отказам и не подменяются этим алгоритмом.

### 13.2. Примеры

| Ответ | Статус | Почему |
|---|---|---|
| `{}` | 2 | Нет обнаруженных полей |
| Только `company_name` | 3 | Имя найдено, адреса нет |
| Только корректный email | 3 | Поле найдено, адреса нет |
| Улица, дом, индекс, город; остальные поля null | 0 | Полный адрес по критерию задания |
| Улица, индекс, город без дома | 3 | Нет `house_no` |

Импорт запрещает пустой `Web`, но код 5 нужен для ранее созданных или вручную изменённых строк. Противоречия нет: проверка CSV и обработка содержимого БД имеют разные границы.

### 13.3. Старые поля после раннего отказа

При ошибке до получения нового результата код обновляет статус и известный Impressum URL, но может сохранить прежние извлечённые поля. Поэтому заполненный `legal_name` при статусе 4 не означает успех последней попытки.

Когда получен результат извлечения, поля заменяются текущим результатом. При анализе нужно смотреть и `status`, и `updated_at`, и `raw_json`.

## 14. Код enrich_companies.py

### 14.1. main()

Разбирает `--company`, `--limit`, `--status`, настраивает журналирование и читает параметры БД. `--limit` должен быть положительным, `--status` — одним из 0–5.

CLI не импортирует Flask и не обращается к HTTP API собственного сервиса. Ему нужна доступная PostgreSQL и окружение. Запуск внутри `web` удобен потому, что там уже установлены библиотеки и переданы переменные.

### 14.2. run()

Создаёт таблицу при необходимости, выбирает snapshot строк, затем последовательно обрабатывает их. Между компаниями выдерживается одна секунда. После каждой попытки отдельно сохраняет изменения и считает итоги.

Счётчики: `selected` — выбрано, `saved` — сохранено, `conflicted` — запись изменилась до сохранения, `failed` — неуспешные результаты/ошибки записи. Счётчики не являются взаимоисключающими: сохранённый статус 4 увеличивает и `saved`, и `failed`.

### 14.3. enrich_one()

Последовательность одной компании:

1. Нормализовать `web`.
2. Получить главную страницу и конечный URL.
3. Найти ссылку Impressum.
4. Загрузить страницу реквизитов, если это другой URL.
5. Удалить служебный HTML и получить текст.
6. Сократить длинный текст и записать метрики.
7. Вызвать извлечение через DeepSeek.
8. Вернуть набор изменений для БД.

Ожидаемые `FetchError` и `DeepSeekError` превращаются в статус 4. Отсутствие ключа — ошибка конфигурации, которая останавливает необходимый API-путь понятным сообщением; код не присваивает из-за неё всем компаниям ERROR.

### 14.4. Код завершения

Exit code 0 означает успешную обработку либо отсутствие выбранных строк. Exit code 1 означает ошибку конфигурации, неуспешный результат или конфликт сохранения.

В PowerShell код последней внешней команды доступен через `$LASTEXITCODE`. Ненулевой код не означает, что весь batch откатился: результаты предыдущих компаний могли сохраниться.

### 14.5. Логи

Логи показывают имя компании, стратегию текста, длину до/после, оценку токенов, номер попытки, usage и итоговый статус. Это делает экономию и отказы наблюдаемыми.

Логи стороннего HTTP-клиента ограничены, чтобы не раскрывать ненужные сетевые детали. Сам ключ, Authorization и полное тело запроса выводить не нужно.

## 15. Как работает рекордер

### 15.1. capture_video.py

Читает `input.csv`, проверяет заголовки и для каждой строки вызывает `qscript.CaptureVideo_Magento(...)`. Если задан `--server`, передаёт полученный путь клиенту загрузки и просмотра.

Так файл входа можно менять без переписывания браузерной функции. Сигнатура сценария фиксирована ТЗ:

```python
CaptureVideo_Magento(
    url, company_name, language, country,
    postcode, city, street, house_no,

```

### 15.2. Playwright и browser context

Playwright управляет браузером: открывает страницы, ожидает элементы, перемещает мышь, вводит текст. Sync API позволяет писать последовательные вызовы без `async/await`.

Browser context — изолированная сессия браузера со своими страницами и настройками. Для записи задаются `record_video_dir`, `record_video_size` и viewport 1280×720.

После сценария нужно закрыть context: это финализирует WebM. Только затем видео получает итоговое имя компании и возвращается абсолютный путь. При ошибке функция возвращает `None`, а цикл может перейти к следующей строке.

### 15.3. Сценарий и эффекты

Сценарий открывает DuckDuckGo, плавно подводит мышь к поиску, посимвольно вводит `Magento developer in <City>`, запускает поиск и переходит к первому результату.

Видеозапись должна показывать действия, поэтому добавлены SVG-курсор, жёлтая подсветка, ripple клика и текстовый callout. DOM-оверлеи имеют `pointer-events: none`, чтобы визуальный слой не перехватывал нажатия.

`add_init_script` внедряет обработчики и на новые документы после навигации. Иначе при переходе на другую страницу курсор и эффекты исчезли бы.

### 15.4. Клиент видео

`UploadVideo()` загружает файл и найденный sidecar. При sidecar инициирует обработку и возвращает обработанный URL. `GetVideoURL()` по прежнему контракту возвращает оригинал. `PreviewVideo()` открывает переданный URL в Chromium.

Приложение хранит байты ролика в файловом томе, а в PostgreSQL — путь, URL и метаданные. Поэтому перенос данных требует учитывать оба тома.

## 16. Зум: события, математика и обработка

### 16.1. Почему зум применяется после записи

Во время записи сохраняется исходное изображение и команды приближения. Затем ffmpeg пересчитывает кадры. Это отделяет сбор действий от тяжёлого кодирования и позволяет обрабатывать файл в Docker.

F5 переключает `in`/`out`; программный `window.__zoomAt(x, y)` делает то же. Событие содержит время от начала записи, координаты и тип. Кольцо показывает оператору переключение.

### 16.2. Sidecar

Sidecar — дополнительный файл рядом с основным, содержащий метаданные. Для `ACME.webm` имя — `ACME.webm.zoom.json`.

```json
{
  "viewport": {"width": 1280, "height": 720},
  "fps": 25,
  "zoom_factor": 2.0,
  "ramp_sec": 0.5,
  "events": [
    {"t": 3.0, "x": 640, "y": 360, "type": "in"},
    {"t": 8.0, "x": 640, "y": 360, "type": "out"}
  ]
}
```

Без событий sidecar не создаётся. Старый формат без `type` во всех событиях трактуется как чередование с `in`. Смешанный старый/новый формат отклоняется. Проверяются время, порядок, координаты, fps, ramp и конечность чисел.

### 16.3. Геометрия crop

При масштабе `z` из кадра `W × H` выбирается прямоугольник `W/z × H/z`, затем растягивается обратно до исходного разрешения. При `z=2` в обеих осях берётся половина размера исходника.

Для целевой точки `(px, py)`:

```text
crop_width  = W / z
crop_height = H / z
x = clamp(px - crop_width / 2, 0, W - crop_width)
y = clamp(py - crop_height / 2, 0, H - crop_height)
```

`clamp` удерживает значение внутри диапазона. Возле края точка не может оставаться строго в центре crop без выхода за кадр, поэтому ограничение границ имеет приоритет.

Совпадение viewport и размера видео даёт отображение координат 1:1. Иначе потребовались бы коэффициенты пересчёта и учёт возможных полей.

### 16.4. Плавность smoothstep

Для нормированного времени перехода `u` от 0 до 1 используется:

```text
ease(u) = u² × (3 - 2u)
z(t) = z_start + (z_target - z_start) × ease(u)
```

Производная smoothstep на концах равна нулю, поэтому движение мягко начинается и заканчивается. Между `in` и `out` масштаб удерживается. Если `out` нет, удерживается до конца.

Длительность округляется до кадров: `max(1, floor(ramp_sec × fps + 0.5))`. При `0.5 × 25` получается 13 кадров, то есть 0.52 секунды. Если новый переход начался раньше завершения прошлого, расчёт начинается с уже достигнутого состояния.

### 16.5. apply_zoom.py

`build_filter()` формирует выражения `zoompan`, `probe()` читает свойства через ffprobe, `process_video()` проверяет вход, кодирует во временный файл и публикует результат через замену после проверки.

Обработчик принимает WebM, создаёт новый `.zoomed.webm`, использует VP9 для видео и Opus для существующего аудио. Проверяет сохранение разрешения и длительности. Без событий выполняется побайтовое копирование без ffmpeg.

Необязательный стартовый цветной маркер помогает совместить часы событий с реальными кадрами: время создания context и первого кадра может различаться.

### 16.6. Jobs и неизменяемый вход

Загрузка с zoom создаёт job со snapshot исходного видео и sidecar. Повторная загрузка компании может обновить `videos`, но не должна менять вход уже созданной задачи.

Состояния: `pending → processing → completed` либо `failed`. Обработка через `POST /jobs/<id>/process` синхронная: запрос ждёт завершения. Отдельной очереди фоновых workers в этой реализации нет.

Успешный результат хранится в `jobs`. Повтор completed возвращает сохранённый результат; одновременная обработка получает 409. После клиентского timeout следует проверить `GET /jobs/<id>`, поскольку timeout HTTP-клиента сам не доказывает остановку серверной работы.

## 19. Проверки и тесты

### 19.1. Что проверяют разные уровни

Unit-тест изолирует алгоритм: CSV, сокращение текста, статусы, геометрию. Интеграционный тест проверяет взаимодействие с PostgreSQL или Flask. Сквозная проверка проходит через работающий HTTP-сервис, контейнеры и файлы.

Mock — подставная реализация внешней зависимости. Для DeepSeek тест задаёт готовый ответ и проверяет поведение программы без ключа, интернета и оплаты. Такие тесты подтверждают логику обработки, но не доступность реального API.

### 19.2. Без платных вызовов, внутри Docker

При запущенном стеке:

```powershell
docker compose exec -T web python scripts/verify_companies.py --server http://127.0.0.1
docker compose exec -T web python -m pytest tests -m "not browser" -q
docker compose exec -T web python -m unittest discover -s tests -v
```

В первой команде порт не указан, потому что проверка выполняется внутри `web`, где Apache слушает 80. Снаружи адрес имеет `:8000`.

Ожидаемый итог скрипта компаний — `ALL COMPANY CHECKS PASSED`. Число pytest-тестов зависит от версии проекта; ориентируйтесь на отсутствие failures/errors и явно учитывайте skips/deselected.

DB-тесты используют отдельную БД `<DB_NAME>_test`. Smoke-скрипт работает с запущенным сервисом, импортирует sample и оставляет проверочные данные. У `verify_companies.py` есть `--live`, но этот флаг включает реальные платные вызовы и не нужен для обычной автоматической проверки.

### 19.3. Локальные проверки алгоритмов

После подготовки виртуального окружения:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_impressum.py tests/test_deepseek_extraction.py -v
.\.venv\Scripts\python.exe -m pytest tests/test_zoom_events.py -v
```

Эти команды подходят для проверки подготовки текста, JSON и чистой математики. Полный набор включает тесты с дополнительными требованиями к БД, браузеру или кодировщику.

### 19.4. Браузер и реальные видео

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_zoom_browser.py -v
.\.venv\Scripts\python.exe scripts/verify_docker.py
.\.venv\Scripts\python.exe scripts/verify_zoom.py --restart
```

Browser-тестам нужен Chromium, скриптам — работающий Docker. `verify_docker.py` перезапускает стек без удаления томов. Сквозная проверка зума выполняет настоящее кодирование в Docker и проверяет свойства результата; `--restart` добавляет проверку сохранности после перезапуска.

Skip означает невыполненную проверку, а не подтверждение соответствующего требования.

### 22.2. Пример связного объяснения

«Мы расширили существующий сервис в Docker. Для компаний добавили отдельную таблицу и форму импорта CSV. Файл полностью проверяется перед записью, затем строки вставляются или обновляются по уникальному имени. Повторный импорт изменяет только исходные CSV-поля и сохраняет результаты извлечения.

Обогащение запускается отдельной программой. Она выбирает ещё неуспешные строки, открывает сайт, ищет ссылку Impressum и получает текст страницы. Перед DeepSeek удаляются служебные элементы HTML. Длинный текст сокращается от юридического заголовка до последнего признака реквизитов с запасами; при недостаточных признаках применяется fallback.

Модель возвращает JSON, но программа дополнительно проверяет его типы и допустимость для БД. Затем назначает статус: пустой результат, неполный адрес или успех. Полный адрес определяется четырьмя компонентами. Результаты сохраняются отдельно по каждой компании, поэтому сетевой сбой одной строки не отменяет остальные. От устаревшего сохранения защищает сравнение updated_at».

### 22.3. Теоретические вопросы

**Почему недостаточно requests без BeautifulSoup?** Requests получает ответ HTTP. BeautifulSoup разбирает HTML-структуру, позволяет искать ссылки и удалять заданные теги. Это разные этапы.

**Почему не отправлять сырой HTML?** Он содержит код, оформление и повторения, которые увеличивают вход. Методичка требует сначала выделить текст и оптимизировать длинные страницы.

**Почему обрезаем после последнего маркера?** Телефон, реестр или ответственное лицо могут стоять ниже адреса. Последний маркер с запасом помогает сохранить конец полезного блока.

**Почему нужен fallback?** На странице может не быть ожидаемого заголовка или сильного сигнала. Жёсткое применение неуверенных границ могло бы удалить реквизиты.

**Точно ли 8000 символов равны 2000 токенов?** Нет, это приблизительная эвристика. Реальный расход нужно смотреть в usage API.

**Зачем JSONB, если есть отдельные колонки?** Колонки удобны для чтения основных полей. JSONB сохраняет вложенный адрес и дополнительные данные извлечения для анализа.

**Почему NULL status не равен ERROR?** NULL означает отсутствие попытки. ERROR означает состоявшуюся неуспешную загрузку или API-вызов.

**Почему без VAT возможен OK?** По §4.6 Task 3 успех требует обнаруженных полей и четырёх компонентов адреса. VAT не входит в обязательную полноту адреса.

**Почему статус 2 определяется раньше 3?** Пустой результат тоже имеет неполный адрес, но должен классифицироваться как отсутствие извлечения.

**Что защищает от дубликатов?** UNIQUE по имени и UPSERT. Advisory lock дополнительно согласует параллельные импорты и их счётчики.

**Что защищает от SQL injection?** Передача значений параметрами, а динамических имён через `sql.Identifier`.

**Что защищает от перезаписи новых данных старым ответом?** Условие сохранения по `id` и исходному `updated_at`. Это optimistic concurrency control.

**Зачем не держать транзакцию во время HTTP?** Сеть медленная и непредсказуемая. Длительная транзакция удерживала бы ресурсы без необходимости.

**Почему не бесконечные повторы API?** Они увеличивают расходы и задержки. Две попытки ограничивают работу одной компании в одном запуске.

**Почему CLI независим от Flask?** Обогащение — пакетная операция с прямым доступом к БД. Её можно запускать по расписанию или вручную без HTTP-запроса к собственному серверу.

**Что сохраняется после удаления контейнеров?** Данные в named volumes, пока тома не удалены. Байты видео и БД находятся в разных томах.

**Чем image отличается от container?** Image — собранная основа, container — запущенный экземпляр с процессами и изменяемым слоем.

**Что такое WSGI?** Интерфейс вызова Python веб-приложения сервером. В проекте его реализует связка Apache/mod_wsgi и Flask.

**Почему зум не меняет разрешение результата?** Маленький crop растягивается обратно до исходного размера кадра; меняется видимая область, а не размер выходного видео.

**Почему курсор возле края не всегда в центре зума?** Центрирование ограничено границами исходного кадра, иначе появились бы области за пределами изображения.

**Можно ли доверять реквизитам модели без проверки?** Ответ проходит структурную валидацию, но она не подтверждает фактическую истинность. Для содержательной проверки нужен исходный Impressum.

## 23. Выводы и ограничения

Лабораторная объединяет обработку табличных файлов, веб-приложение, SQL, контейнеризацию, сетевые запросы и применение LLM. Основной результат Task 3 — воспроизводимый процесс превращения исходного списка компаний в сохранённые структурированные реквизиты с наблюдаемым статусом.

Главный алгоритмический вклад — подготовка текста: сначала удаление служебного HTML, затем поиск границ юридического блока, проверка anchors и ограничение объёма. Экономия измеряется по длине текста и usage; её нельзя гарантировать одинаковой для всех сайтов.

Практические ограничения:

- JS-only ссылки и реквизиты могут не попасть в HTML Requests; браузерный fallback отсутствует.
- Удаление заданных тегов и head/tail window способны потерять полезный текст.
- Структурно правильный JSON может содержать ошибочные факты; исходную страницу нужно сохранять как источник проверки через `impressum_url`.
- OK означает критерий адреса лабораторной, а не проверку всей юридической информации.
- Не-OK строки при новом default-запуске снова обрабатываются и могут повторно расходовать API.
- Параллельное обогащение одной строки способно дублировать API-расход, несмотря на защиту сохранения.
- CLI работает последовательно, а обработка jobs синхронная; отдельная очередь задач не реализована.
- Внешние сайты и API могут изменять HTML, доступность и ответы; это требует диагностики, а не подстановки выдуманных данных.
