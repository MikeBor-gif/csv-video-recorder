# Зум записанных видео — Internship Task 2

При записи собираются точки и время переключения зума. Изображение страницы в браузере не масштабируется: цветное кольцо только подтверждает переключение. После записи ffmpeg применяет эффект `zoompan` к видео.

## Быстрая проверка без внешних сайтов

Нужны Docker Compose v2 и Python 3.9+. Скрипт использует только стандартную библиотеку Python; ffmpeg работает внутри контейнера.

```bash
docker compose up --build -d --wait
python scripts/verify_zoom.py
```

Скрипт создаёт семисекундный контрастный WebM в `web`, загружает его с событиями, вызывает обработку и проверяет PostgreSQL, разрешение, длительность, изменение кадров и копирование без событий. Ожидаемый итог — `ALL ZOOM CHECKS PASSED`. URL результата выводится для просмотра в браузере. В локальной БД и томе остаются записи проверки с уникальными именами.

Если есть эталонный ролик проекта:

```bash
python scripts/verify_zoom.py --video output.webm --restart
```

`--video` принимает валидный WebM 1280×720 длительностью не менее 6 секунд. `--restart` дополнительно перезапускает `web` и `db` и проверяет сохранность результата; тома не удаляет. Не используйте этот флаг во время другой обработки.

## Запись с F5 или программным hook

Установите зависимости рекордера по [README](../README.md), затем Chromium:

```bash
python -m playwright install chromium
python capture_video.py input.csv --server http://localhost:8000
```

Первый F5 отмечает `in` в текущей точке мыши, следующий — `out`. Повтор клавиши при удерживании игнорируется; F5 не перезагружает страницу. Короткое зелёное кольцо означает in, розовое — out. После перехода страницы состояние сохраняется.

Сценарий может вызвать тот же toggle через `await window.__zoomAt(x, y)` в JavaScript. Из Python с Playwright sync:

```python
page.evaluate("() => window.__zoomAt(640, 360)")  # in
# Действия сценария; эта пауза определяет удержание зума.
page.evaluate("() => window.__zoomAt(640, 360)")  # out
```

Hook принимает координаты viewport текущего документа, возвращает Promise с принятым событием. Программный hook не перемещает мышь. F5 и hook работают также внутри iframe, включая вложенные фреймы другого origin: координаты пересчитываются в viewport основной страницы, индикатор появляется на ней. Сторонние popup не добавляют события к ролику основной страницы.

Демонстрационный режим вызывает hook до и после ввода поискового запроса; автоматизация не нажимает F5:

```bash
python capture_video.py input.csv --zoom-demo --server http://localhost:8000 --view-seconds 10
```

Без `--zoom-demo` автоматических событий нет. Когда событий нет, JSON не создаётся; успешная перезапись обычного видео удаляет старый sidecar с тем же именем. Ошибка одной CSV-строки не останавливает следующие.

При старте записи появляется короткий маркер 16×16 px в левом верхнем углу. Он позволяет согласовать часы событий с первым реальным кадром, поскольку создание browser context и начало видеопотока происходят в разное время. Калибровка выполняется при обработке в Docker; ffmpeg на машине рекордера для этого не нужен.

## Sidecar

Для `ACME.webm` файл называется **`ACME.webm.zoom.json`**:

```json
{
  "viewport": {"width": 1280, "height": 720},
  "fps": 25,
  "zoom_factor": 2.0,
  "ramp_sec": 0.5,
  "events": [
    {"t": 3.0, "x": 640, "y": 360, "type": "in"},
    {"t": 8.0, "x": 640, "y": 360, "type": "out"}
  ]
}
```

Запись добавляет необязательный объект `calibration` с временем и идентификатором стартового маркера. Старые sidecar без этого объекта остаются поддержаны: их `t` непосредственно означает секунды видео. При наличии calibration ffmpeg сначала находит кадр маркера и корректирует временную шкалу.

Размер viewport должен совпадать с размером видео: координаты мыши и пиксели видео соответствуют 1:1. События идут по времени и чередуются in/out. Поддерживаются несколько пар; открытый in удерживается до конца видео без искусственного out. Центр пары задаётся точкой in; out начинает отдаление от достигнутого масштаба.

Масштаб меняется по smoothstep easing. Ramp округляется к числу кадров: `max(1, floor(ramp_sec * fps + 0.5))`, поэтому 0.5 s при 25 fps даёт 13 кадров. Crop ограничен краями изображения. Новый in во время отдаления плавно продолжает от текущего масштаба и центра.

Legacy-файлы, в которых **все** события без `type`, интерпретируются как чередование in/out, начиная с in. Смешивать старые и typed-события нельзя. Неконечные числа, отрицательное время, неверный порядок и координаты вне viewport дают ошибку; события не сортируются молча.

## CLI обработки

При локальном кодировании нужны ffmpeg с `libvpx-vp9` и ffprobe. В Docker они уже установлены.

```bash
python apply_zoom.py --video video/ACME_GmbH.webm
python apply_zoom.py --video video/ACME_GmbH.webm --dry-run
python apply_zoom.py --video video/ACME_GmbH.webm --ffmpeg /usr/bin/ffmpeg
```

По умолчанию выход — `video/ACME_GmbH.zoomed.webm`. Дополнительные опции: `--output` и `--sidecar`. Они нужны, например, для обработки серверных снимков исходников. Явно указанный отсутствующий sidecar считается ошибкой.

`--dry-run` печатает команду без кодирования, временных файлов и требования установленного ffmpeg. Для калиброванного sidecar команда показывает исходные времена; при реальном запуске они уточняются по маркеру. Без событий печатается операция копирования.

При реальном кодировании фильтр передаётся через временный файл: множество событий не должно превышать лимит длины команды Windows. Временной ряд формируется сбалансированным выражением, чтобы не упираться в глубину parser ffmpeg. Поддержаны загрузка фильтра из файла в новых версиях и legacy-вариант Docker ffmpeg 5.1; временный файл удаляется после выполнения.

Обработка принимает исходники с расширением `.webm`; загрузка с multipart `zoom` также требует `.webm`. Прежняя загрузка без `zoom` продолжает принимать остальные поддерживаемые форматы. `zoom_factor` должен быть от 1 до 10 включительно — это диапазон ffmpeg zoompan.

Нет sidecar либо events пуст — выход является побайтовой копией оригинала WebM, ffmpeg не запускается. Неверный JSON не считается отсутствием событий. При реальном кодировании создаётся отдельный WebM того же разрешения с VP9; имеющееся аудио перекодируется в Opus. Исходник не перезаписывается. Результат публикуется после успешной проверки, временный файл при ошибке удаляется.

## Upload и jobs API

`UploadVideo(server_url, video_path, company_name)` автоматически находит sidecar, отправляет его и запускает обработку. С sidecar функция возвращает обработанный URL, без него — прежний URL оригинала. Существующий preview открывает возвращённый URL.

Ручной HTTP-вызов состоит из двух шагов:

```bash
curl -F "file=@video/ACME_GmbH.webm" -F "company_name=ACME GmbH" -F "zoom=@video/ACME_GmbH.webm.zoom.json" http://localhost:8000/upload
```

Upload возвращает `company_name`, URL оригинала `video_url` и `job_id`. Далее вызовите `POST /jobs/<job_id>/process`; `<job_id>` нужно заменить полученным UUID. Без sidecar `/upload` возвращает только прежние `company_name` и `video_url`.

| Маршрут / состояние | Результат |
|---|---|
| `GET /jobs/<id>` | Статус, URL оригинала, `processed_video_url`, безопасная ошибка |
| `POST /jobs/<id>/process`, pending или failed | Синхронное кодирование; 200 completed с URL либо 500/504 failed |
| Уже processing | 409; второй ffmpeg не запускается |
| Уже completed | 200 с прежним результатом без перекодирования |
| Неизвестный UUID | 404 |

URL результата и состояние хранятся в таблице `jobs`; схема `videos` сохраняется. `GetVideoURL` и `/get_video_url` по-прежнему возвращают оригинал. Каждая задача читает отдельный неизменяемый snapshot: повторная загрузка компании не подменяет вход уже созданной задачи. `.jobs` и промежуточные файлы недоступны через HTTP.

Состояния: pending → processing → completed/failed. Failed можно повторить. После аварийного завершения истёкший processing переводится в failed при GET/process; затем разрешён retry. Это синхронный endpoint, постоянного фонового worker нет.

## Настройки и диагностика

| Переменная | Default | Назначение |
|---|---|---|
| `FFMPEG_PATH` | `ffmpeg` | Binary внутри processing-контейнера; ffprobe рядом или в PATH |
| `ZOOM_PROCESS_TIMEOUT` | `300` | Лимит кодирования в секундах |
| `ZOOM_HTTP_TIMEOUT` | `600` | Apache/WSGI timeout; должен превышать лимит обработки минимум на 120 s |
| `ZOOM_LOG_LEVEL` | `INFO` | DEBUG/INFO/WARNING/ERROR для обработчика |
| `WEB_SERVICE_LOG_LEVEL` | `INFO` | Уровень web-service логов |
| `QSCRIPT_LOG_LEVEL` | `INFO` | DEBUG/INFO/WARN/ERROR рекордера и клиента |

Значения Docker задаются в `.env`; при изменении лимита задайте тот же `ZOOM_PROCESS_TIMEOUT` в окружении локального клиента. Его HTTP timeout включает дополнительный запас 120 s. До и после кодирования есть короткие ffprobe/калибровочные шаги; deadline задачи учитывает запас 90 s.

При timeout клиента оригинал мог уже загрузиться, а сервер мог продолжить работу. `VideoClientError` содержит job_id: проверьте `GET /jobs/<id>`, прежде чем повторять обработку. Ошибки ffmpeg и внутренние пути доступны в серверных логах, а не в ответе API.

```bash
docker compose logs web
```

DuckDuckGo может не отдать результаты или ограничить автоматизацию. Это приводит к FAILED строки; проверяйте механику зума локальными browser-тестами и Docker-скриптом независимо от внешнего сайта.

## Тесты

В Docker dev-зависимости уже установлены. Локально:

```bash
python -m pip install -r requirements-dev.txt
python -m playwright install chromium
python -m pytest tests/test_zoom_events.py tests/test_apply_zoom.py tests/test_zoom_capture.py -v
python -m pytest tests/test_zoom_browser.py -v -s
```

Для Linux-хоста установка mod-wsgi требует системных заголовков Apache и компилятора, как описано в README. Чистые pytest-тесты не требуют ffmpeg/БД/браузера; browser-тесты требуют Chromium, тест калибровки и кодирования — ещё и локальные ffmpeg/ffprobe. Отсутствие этих инструментов обозначается skip.

```bash
docker compose exec -T web python -m pytest tests/test_zoom_events.py tests/test_apply_zoom.py tests/test_zoom_capture.py tests/test_zoom_service.py tests/test_video_client.py tests/test_web_service.py -v
docker compose exec -T web python -m unittest discover -s tests -v
python scripts/verify_docker.py
```

Service-тесты используют отдельную `<DB_NAME>_test` (либо `TEST_DB_NAME`) и временные каталоги. `TEST_DB_NAME` должен отличаться от рабочей БД и не может быть `postgres`, `template0` или `template1`: небезопасная настройка отклоняется до подключения. Unittest сохраняет регрессию прежнего API; для покрытия Task 2 обязательно запускать pytest. Старый verify_docker проверяет загрузку байтов и перезапускает стек через down/up; новый verify_zoom действительно кодирует валидное видео. Skipped проверки не доказывают полную приёмку.
